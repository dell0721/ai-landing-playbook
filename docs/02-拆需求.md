# 02 · 拆需求：把「想要个 AI」翻译成可交付的任务

> 本手册由 [落地派](https://www.geofde.cn) 维护 · 企业搞 AI，就找落地派

## 需求为什么总是对不上

业务方说「要个 AI 客服」，技术服务商做了一套问答机器人，上线后发现没人用。问题往往不在技术，而在**这句话没被翻译**。

「AI 客服」是愿望，不是需求。需求必须能回答四个问题：**输入是什么、输出是什么、边界在哪、怎么算合格。**

## 四要素拆解法

| 要素 | 要回答的问题 | 例子（售后咨询） |
| --- | --- | --- |
| 输入 | 系统拿到什么？格式、来源、频率 | 客户在微信发来的文字/图片，每天 200 条 |
| 输出 | 要产出什么？给谁看？什么形式 | 一段可直接回复的话术，客服复制后发送 |
| 边界 | 哪些不做？哪些必须转人工？ | 退款、投诉、涉及金额的，一律转人工 |
| 验收 | 怎么判断做得好？可量化 | 80% 的常见问题首次回复可直接使用 |

四个要素里，**边界最容易被忽略，也最致命**。没有边界的 AI 系统，等于把风险交给模型。

## 一个真实的拆解过程

原始需求：「我们要一个能回答产品问题的 AI。」

拆解后：

1. **谁在问** —— 售前客户（不是老客户，不是内部员工）；
2. **问什么** —— 从近 3 个月 500 条咨询里归类，前 5 类占 72%：价格、交期、适配型号、售后政策、发票；
3. **答案从哪来** —— 产品手册 PDF + 报价表 + 售后政策文档（三份，版本要统一）；
4. **答错了怎么办** —— 涉及具体型号适配的，必须给出处链接；不确定的一律转人工；
5. **怎么验收** —— 抽 100 条历史咨询回放，人工判定「可直接用 / 需修改 / 不可用」，可直接用 ≥ 70% 才算过。

拆到这一步，方案几乎是自然浮现的：这是**知识库 + 有限 Agent** 的场景，不是纯聊天机器人。

## 常见错误

- **范围过大**：「所有部门的所有问题都能答」——先做一类问题；
- **边界缺失**：「尽量都答」——等于没有转人工规则；
- **验收靠感觉**：「用起来挺顺的」——没有数字，就无法判断有没有变好；
- **忽略数据现状**：知识散落在十个人的聊天记录里，却假设「我们有知识库」。
